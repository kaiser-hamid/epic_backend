# Blood Bank Module — Implementation Plan

Source: `brief.md` (scope) and `README.md` / `CLAUDE.md` (conventions). Items marked **[confirm]** depend on the open questions in brief section 7. Model them so they are configurable data (lookup tables, enums that are easy to extend), not hard-coded behaviour.

## Phase 1: Database schema (migrations + models)

Work order: Shared prerequisites, then Blood Bank tables in dependency order, then models, factories and seeders.

### 1.1 Conventions for every table

- Location: `modules/BloodBank/Database/Migrations/`, prefix `bb_`, loaded by `BloodBankServiceProvider` (`loadMigrationsFrom`).
- `id` bigint primary key, `timestampsTz()`, foreign keys always with constraints, indexes on every FK and on every searchable column.
- No hard deletes of business records: `softDeletesTz()` on master/registration data, status columns on workflow records.
- Human-facing numbers (`case_no`, `donor_no`, `sample_no`, `unit_no`, ...) are unique string columns generated by the Shared Numbering service.
- Status/type columns are strings cast to PHP Enums on the model (no DB enums, so values can change without a migration). Enums live in `modules/BloodBank/Enums/`.
- Actor columns (`*_by`) are FKs to the Shared users table.
- `jsonb` only for configuration/snapshots, never for queried data.
- Results, eligibility decisions, stock transactions and movement history are append-only: corrections create a new row (new version) with a reason.
- Models: `final`, `HasFactory`, enum casts, relationships, scopes only (no workflows). Under `shouldBeStrict()`, declare `$fillable` and eager-load deliberately.
- Create files with `php artisan make:model` / `make:migration` (use `--path` / move into the module folder), plus a factory and seeder per model.

### 1.2 Shared prerequisites (check first; build in `modules/Shared` if missing)

| Table | Purpose for Blood Bank |
|---|---|
| `sh_patient_master` | Patient master, mirroring the vendor registration form: `patient_no`, `vendor_patient_id`, title, name, address, age (years, months, days), date of birth, gender, marital status, blood group, phone, `national_id`. Blood Bank stores only `patient_master_id`. |
| `sh_billing` | Invoice header, generated by the Shared module, never by Blood Bank: `invoice_no` (`{2-letter branch code}{yyMMdd}{4-digit counter}`, per branch and reset daily, from the Numbering service; patient `patient_no` is `P{yyMMdd}{4-digit}`, global and reset daily), `patient_master_id`, `branch_id`, `amount` (total in paisa, computed server-side), `status`, `billed_at`. Lines live in `sh_billing_items` (`billing_id`, `test_item_id`, `quantity`, `rate` snapshot, `amount`); department, code and name come from the catalog. Referral data lives in `sh_billing_referrals`. Patient type and discount are deliberately not modelled yet. Blood Bank stores only `billing_id`. |
| `sh_doctors` | Doctor master (`code`, `name`, `degree`, `address`, `phone`, `is_active`), referenced by `sh_billing`. Lives in `modules/Shared/Doctor` because OPD and other modules will reuse it. |
| `sh_departments`, `sh_test_items` | Shared catalog in `modules/Shared/TestCatalog`: departments (`code`, `name`) and billable test items (`department_id`, `code` = Item ID, `name`, `rate` in paisa). Not the same as `bb_test_definitions`, which describes Blood Bank lab test result fields. |
| Numbering sequences | One sequence per Blood Bank number type. |
| Users, roles, permissions, `sh_audit_logs` | Actors, RBAC and audit. |

### 1.3 Blood Bank tables

**A. Case and donor registration**

| Table | Key columns | Notes |
|---|---|---|
| `bb_cases` | `case_no`, `patient_master_id` (FK `sh_patient_master`), `billing_id` (FK `sh_billing`, nullable), `care_type` (daycare/out), `transfusion_reason` (nullable), `reference_note`, `status`, `supplied_at` (nullable), `created_by` | One Blood Bank case for a patient. Patient details are read from the patient master, not copied. The consultant is the referring doctor in `sh_billing_referrals`, not stored here. |
| `bb_case_components` | `case_id`, `component_type_id`, `quantity` | Requested components for the case. Unique (`case_id`, `component_type_id`). Fulfilled by units assigned to the case (`bb_units.case_id`) of the same type. |
| `bb_donors` | `donor_no`, `name`, `date_of_birth` / `age`, `gender`, `blood_group`, `phone`, `address`, `national_id`, soft deletes | Unique person ID, reused across cases (not barcoded). Sensitive fields are restricted by permission. A donor is a person and may donate for several cases over time. |
| `bb_case_donors` | `case_id`, `donor_id`, `billing_id` (FK `sh_billing`, nullable), `sequence_no`, `status` (registered, eligible, deferred, collected) | Links donors to a case. A new donor is a new row with the next `sequence_no`; the earlier row keeps its status for history. `billing_id` holds the new bill for a replacement donor. Unique (`case_id`, `donor_id`). |

**B. Samples and tests**

| Table | Key columns | Notes |
|---|---|---|
| `bb_test_definitions` | `code`, `name`, `result_type`, `unit`, `reference_range`, `options` (jsonb), `applies_to` (patient/donor/both), `sort_order`, `is_active` | Configurable predefined tests **[confirm names and fields; described as five]**. |
| `bb_samples` | `sample_no`, `case_id`, `case_donor_id` (nullable), `subject_type` (patient/donor), `collected_at`, `collected_by`, `status` | Patient or donor sample. Exactly one of the patient/donor subject is set. |
| `bb_test_results` | `sample_id`, `test_definition_id`, `version`, `is_current`, `result_value`, `observation`, `tested_by`, `tested_at`, `status`, `reviewed_by`, `reviewed_at`, `amendment_reason` | Versioned: an amendment inserts a new version and clears `is_current` on the old one. Unique (`sample_id`, `test_definition_id`, `version`). |
Eligibility (accepted/deferred) is recorded on `bb_case_donors` (`status`, `deferral_reason`, `assessed_by`, `assessed_at`); a human decision only, history via the audit log. `eligible` means fit to donate.

| `bb_crossmatches` | `case_id`, `patient_sample_id`, `unit_id`, `major_result`, `minor_result` (compatible/incompatible), `remarks`, `status`, `tested_by/at`, `reviewed_by/at`, `version`, `is_current`, `amendment_reason` | Patient sample vs one unit (bag), so it also covers units supplied from storage without a donor. Printed as the Compatibility Test Report (`bb.compatibility_report`). Versioned like test results. |

`bb_test_definitions` also has `method` (printed on the report). Physical examination is in `bb_donor_screenings`.

**C. Collection, components, storage**

| Table | Key columns | Notes |
|---|---|---|
| `bb_storage_locations` | `code`, `name`, `type`, `min_temperature_c`, `max_temperature_c`, `is_active` | Fridge/freezer/shaker etc. **[confirm; temperature records may be required]**. |
| `bb_collections` | `bag_no`, `case_donor_id`, `volume_ml`, `collected_at`, `collected_by`, `approved_by`, `status`, `notes` | One blood draw into one bag, linked to donor and case. `bag_no` is unique, generated by the numbering service and printed as the bag label. |
| `bb_component_types` | `code`, `name`, `shelf_life_hours`, `storage_condition`, `default_location_type`, `is_active` | Whole blood, PCV, FP, CRYO, PLATELET, PLASMA **[confirm official terminology and expiry rules]**. Expiry rules are data here, not code. |
| `bb_units` | `unit_no`, `collection_id`, `parent_unit_id` (self FK, nullable), `component_type_id`, `blood_group`, `volume_ml`, `status`, `storage_location_id`, `prepared_at`, `expires_at` | One row per whole-blood unit and per derived component. `parent_unit_id` gives traceability back to source. One barcode per physical bag: the whole-blood unit's `unit_no` is its `bag_no`; a component's is `bag_no-CODE` (e.g. `BB-B-000123-PCV`), with `-n` for splits (`UnitNumberGenerator`). Statuses: available, reserved, issued, quarantined, discarded, expired. Index (`status`, `expires_at`) for the expiry dashboard. |
| `bb_unit_movements` | `unit_id`, `from_status`, `to_status`, `from_location_id`, `to_location_id`, `reason`, `performed_by`, `occurred_at` | Append-only status and location history. |

**D. Printing**

| Table | Key columns | Notes |
|---|---|---|
| `sh_print_logs` (Shared, `modules/Shared/Printing`) | `document_type`, `printable_type`, `printable_id`, `printed_by`, `printed_at`, `is_reprint`, `reprint_reason` | Records every print and reprint (audit requirement) for all modules. Blood Bank records prints through the `PrintLogger` contract; `PrintDocumentType` values are `bb.`-prefixed and printables use morph aliases (`bb.sample`, `bb.collection`, `bb.unit`, `bb.case`). `is_reprint` is decided server-side and a reprint without a reason is rejected (`REPRINT_REASON_REQUIRED`). Label and report templates themselves are views, not tables **[confirm sizes, barcode format, fields]**. There are no barcode columns: a label's barcode encodes `sample_no` (patient and donor samples), or `unit_no` (every bag: equals `bag_no` for whole blood, `bag_no-CODE` for components), and a scan looks the record up by that number. |

**E. Consumable inventory**

| Table | Key columns | Notes |
|---|---|---|
| `bb_consumables` | `code`, `name`, `unit_of_measure`, `minimum_stock`, `tracks_batch`, `tracks_expiry`, `is_active`, soft deletes | Catalog. `minimum_stock` drives low-stock warnings. |
| `bb_consumable_batches` | `consumable_id`, `batch_no`, `expires_at`, `quantity_on_hand` | Only used for items that track batch/expiry. |
| `bb_consumable_transactions` | `consumable_id`, `batch_id` (nullable), `type` (received/issued/adjusted), `quantity`, `balance_after`, `reason`, `performed_by`, `occurred_at` | Append-only ledger. Quantities are `decimal(12,3)`; current balance is derived from the ledger and cached on the consumable/batch row. |

### 1.3a Status (as built)

- Built: all tables above in `modules/BloodBank/Database/Migrations/`, 17 models, factories, 15 enums, `BloodBankServiceProvider`, and `tests/Feature/SchemaTest.php` (21 passing on the SQLite test config).
- Shared tables built in `modules/Shared` (Patient, Billing sub-folders, `SharedServiceProvider`): `sh_patient_master`, `sh_billing`, with models, factories and the Gender / BloodGroup / BillingServiceType / BillingStatus enums. Shared migrations are dated before Blood Bank ones so they run first.
- Invoices are generated by the Shared billing module, not Blood Bank. `bb_case_invoices` was removed. Blood Bank models hold the IDs only and have no relationship to Shared models (module boundary rule); patient and bill data will be read through a Shared contract when the Actions are built.
- Collection model is named `Collection`; watch for clashes with `Illuminate\Support\Collection` when importing.
- Pending: run `php artisan migrate` against PostgreSQL (needs `.env` and the `diagnostic_erp` / `diagnostic_erp_test` databases), seeders for component types / storage locations, and arch tests.

### 1.4 Creation order

1. `bb_cases`, `bb_donors`, `bb_case_donors`
2. `bb_test_definitions`, `bb_samples`, `bb_test_results`
3. `bb_storage_locations`, `bb_collections`, `bb_component_types`, `bb_units`, `bb_unit_movements`
4. `bb_case_components`, `bb_crossmatches` (print logs live in Shared as `sh_print_logs`)
5. `bb_consumables`, `bb_consumable_batches`, `bb_consumable_transactions`

Each step: migration, model, enum(s), factory, seeder (lookups such as component types and test definitions get seeders with placeholder values until confirmed), and a Pest test that the migration runs and the factory builds a valid row.

### 1.5 Phase 1 done when

- `php artisan migrate:fresh --seed` succeeds on PostgreSQL.
- Every model has a factory; relationships are covered by tests.
- Arch tests pass: Blood Bank models are not used by other modules, and Blood Bank does not import Shared models directly where a contract exists.
- Pint and Larastan are clean.

## Phase 2: Registration and search

Case registration with invoice reference scan/entry, donor registration, multiple donors per case, search by invoice number and patient identifiers. Actions, Data objects, Queries, Resources, module routes, permissions.

## Phase 3: Samples, tests, eligibility, reports

Sample collection, test result recording and versioned amendment, review/approval, eligibility decisions, report PDF (mpdf) in the approved format.

## Phase 4: Collection, components, labels, storage, expiry

Blood collection, component preparation, unit numbering and barcodes, label printing, storage assignment, status movements, hourly expiry alert job, expiry dashboard.

## Phase 5: Consumable inventory

Catalog, receive/issue/adjust transactions, low-stock and expiry warnings, history views.

## Phase 6: Validation and go-live

Permissions seeded per role, audit coverage check for all critical actions, printed outputs verified with Blood Bank staff, backup and retention confirmed.

## Open decisions to resolve before or during Phase 1

1. Predefined tests: names, fields, result types (drives `bb_test_definitions`).
2. Eligibility and deferment statuses, and who may approve.
3. Component terminology, processing workflow and expiry per component/storage condition.
4. Whether temperature logging is required (would add `bb_temperature_logs`).
5. Reservation, issue, return, discard and quarantine rules (the brief tracks these as unit statuses only; blood requests, crossmatch and issue-to-patient workflows from the README are not in this brief's scope).
6. Which consumables need batch and expiry tracking.
7. Label sizes, barcode format, report fields and signatures (affects Phase 3 and 4, not the schema).
